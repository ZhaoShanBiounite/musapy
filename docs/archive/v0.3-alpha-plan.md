## 1. v0.3-alpha Scope

### 1.1 In Scope

| Component | Implementation | Basis |
|---|---|---|
| linalg: matmul / dot / lu / qr / svd / solve | **muBLAS + muSOLVER** (C ABI, no hand-written math kernels) | L4-1 (`dot` is a supplement, 003-D6) |
| random: rand / randn / uniform / normal / bernoulli | **muRAND** | L4-1 |
| fft: fft / fftn / ifft / rfft | **muFFT** (prerequisite: complex64/128 enablement) | L4-1 |
| sparse: csr_matrix / coo_matrix / spmv / spmm | **muSPARSE** | L4-1 |
| reduction completion: `axis=tuple` multi-axis, complex sum/mean | extend `reduction.mu` + kernel instantiation | 002-D3 |
| advanced indexing: boolean mask / fancy indexing | extend `indexing.mu` + `__getitem__` | 002-D4 |
| error model extension: new `LinAlgError` (subclass of `MusapyError`; singular matrix, etc.); advanced-indexing OOB raises **Python built-in `IndexError`** (NumPy-compatible) | ops layer | L3-5 extension (003-D3) |
| per-op CPU fallback (host libs / pure Rust) + mock stubs | v0.2 convention | testable without GPU |

**Overall implementation principle (key)**: L4-1 already locks the math libraries to
MUSA SDK's own wheels. The local SDK 3.1.0 has muBLAS / muSOLVER / muRAND / muFFT /
muSPARSE fully installed (headers + `.so`, verified — see §2). v0.3 **adds no
hand-written math kernels**, only a Rust FFI binding layer. New `.mu` kernels are limited
to the two completion items: advanced indexing (mask / fancy) and complex reduction.

**L2-3 boundary clarification (record in ADR-003)**: L2-3 states musapy-core "may depend
only on the MUSA runtime API, no MUBLAS calls", yet its responsibility table also lists a
"MUBLAS handle table". v0.3 draws the boundary as follows: `musa_x_ffi.rs` (extern decls)
and `math_handle.rs` (handle/plan/generator lifecycle) are **thread-safe global
infrastructure** and live in musapy-core; all **compute calls** (gemm/getrf/fft/spmv etc.)
are issued only from musapy-ops; the **linking** of the 5 MUSA-X libraries is emitted by
musapy-ops/build.rs, and musapy-core/build.rs stays musart-only (its L2-3 comment remains
valid).

**CPU fallback vs L4-2**: L4-2 defers the **standalone `musapy-cpu` crate** (v2+). The CPU
fallback here is the **in-op embedded path** (v0.2 convention, already implemented for
elementwise/comparison/indexing) — no conflict.

### 1.2 Out of Scope (Deferred)

| Component | Deferred to |
|---|---|
| batched matmul (3D+ broadcasting semantics) | evaluate strided-batched late v0.3 / v0.4 (SDK already has `mublasSgemmStridedBatched`) |
| eigh (eigendecomposition) | v0.4 candidate (verified `musolverSsyevd/Dsyevd` exist in 3.1.0; deferral is scope management, not an SDK gap) |
| sort / argsort | v0.4+ (muThrust parallel_for issue unconfirmed fixed; not adopted) |
| DLPack interop | v0.4-beta |
| NumPy protocol (`__array_ufunc__` etc.) | v0.4-beta |
| MUSA Graphs capture | v2 |
| MCCL distributed | v2 |
| kernel fusion / JIT / autotuning | v3+ |
| mixed basic + fancy combined indexing | v0.4 |
| fft multi-shape plan caching | optional late v0.3 |

> Basis note: Graphs / MCCL / JIT / autotuning exclusions come from **L4-2**; the
> v0.4-beta timing for DLPack and NumPy protocol comes from **L4-5** (v0.4-beta =
> interop + error model + observability); their v1 design decisions are L2-6 /
> L3-16~L3-20 (DLPack) and L3-17 / L3-18 (NumPy protocol).

### 1.3 Definition of Success

The following Python code runs end-to-end on MUSA hardware:

```python
import musapy as ms

ms.set_default_device("musa:0")

# ---- linalg (L4-1: muBLAS + muSOLVER) ----
a = ms.array([[1.0, 2.0], [3.0, 4.0]])          # (2,2) float32
b = ms.array([[5.0, 6.0], [7.0, 8.0]])
c = ms.matmul(a, b)                               # (2,2)
x = ms.solve(a, ms.array([1.0, 2.0]))             # solve a·x = b
q, r = ms.qr(a)                                   # QR (reduced)
u, s, vh = ms.svd(a)                              # SVD, s descending
lu, piv = ms.lu(a)                                # LU ((LU, pivots) aligned with torch.linalg.lu)

# ---- random (L4-1: muRAND) ----
r1 = ms.random.rand((2, 3))                       # [0,1) uniform
r2 = ms.random.randn((2, 3))                      # standard normal
r3 = ms.random.uniform(-1.0, 1.0, (4,))           # [-1, 1)
r4 = ms.random.bernoulli(0.5, (4,))               # {0,1} bool

# ---- fft (L4-1: muFFT, complex enablement) ----
f = ms.fft.fft(ms.array([1.0, 2.0, 3.0, 4.0]))    # complex64 output
g = ms.fft.ifft(f)                                # inverse (normalization 1/N)
rf = ms.fft.rfft(ms.array([1.0, 2.0, 3.0, 4.0]))  # real input → shape (N//2+1,)

# ---- sparse (L4-1: muSPARSE) ----
csr = ms.sparse.csr_matrix(
    (ms.array([1.0, 2.0, 3.0]), ms.array([0, 2, 3]), ms.array([0, 1, 1, 4])),
    shape=(3, 4),
)
y = csr @ ms.array([1.0, 2.0, 3.0, 4.0])          # spmv

# ---- reduction completion (002-D3) ----
s2 = ms.sum(a, axis=(0, 1))                       # tuple multi-axis → 0-dim
s3 = ms.sum(a, axis=(0,), keepdims=True)          # shape (1,2)
sc = ms.sum(ms.array([1+2j, 3+4j], dtype=ms.complex64))  # complex sum

# ---- advanced indexing (002-D4) ----
mask = a > 2.0
sel = a[mask]                                     # boolean mask → 1D copy
fancy = a[ms.array([[0, 1], [1, 0]])]             # fancy indexing → copy, (2,2)

ms.Stream("musa:0").synchronize()
print(c.tolist(), x.tolist(), s.tolist())
```

> Note: the complex-related lines (`ms.array([1+2j, ...], dtype=ms.complex64)`, complex sum,
> reading back complex fft output) depend on P5.1 complex enablement — v0.2's `ms.array`
> complex creation and the complex branches of `tolist()`/`item()` all raise
> `NotImplementedError` (verified in musapy-python ops.rs/array.rs). The §1.3 end-to-end
> validation is therefore scheduled after Phase 5 (P9.2).

## 2. Prerequisites

v0.2-alpha verified MUSA SDK health, stream-ordered alloc/free, stride-aware kernels,
and GPU correctness. New v0.3 prerequisites (must be completed in **Phase 1**):

- **MUSA-X libraries present locally (verified)**: `/usr/local/musa/lib/` contains
  `libmublas.so`, `libmusolver.so`, `libmurand.so`, `libmufft.so`
  (+ `libmtfft-device-*.so` per-arch variants), `libmusparse.so`;
  `/usr/local/musa/include/` contains `mublas.h`, `musolver.h`, `murand.h`,
  `mufft.h`, `musparse.h`. SDK version **3.1.0** (mp_21/mp_22, matches MTT S4000).
  The musapy-core `build.rs` comment already reserves this: "those are v0.3+ matters".
- **muSOLVER routine coverage (header-level audit completed 2026-08-06, P1.1 bulk
  done early)**: `getrf / getrs / geqrf / gesvd` all present for S/D/C/Z; `orgqr` only
  S/D (complex counterpart `cungqr` C/Z); `syevd` S/D (+Batched) present;
  **`gesdd` absent** (unusable as a gesvd substitute). Key difference: musolver has
  **no separate Dn handle** — every routine takes `mublasHandle_t`, e.g.
  `musolverSgetrf(mublasHandle_t handle, ...)`, sharing the muBLAS handle and
  `mublasStatus_t`. Remaining P1.1 work: runtime symbol verification (.so vs headers)
  + bufferSize/auxiliary routine inventory.
- **Host OpenBLAS detection**: CPU fallback prefers host OpenBLAS (cblas / lapacke);
  if absent, compile-time degradation to pure-Rust naive implementations (correctness
  only, no performance promise). `apt install libopenblas-dev` recommended.
- **complex dtype status**: musapy-core `dtype.rs` already has Complex64 / Complex128
  with type promotion (`is_complex()`), but: ① elementwise / reduction kernels are not
  instantiated for complex; ② on the Python side, `ms.array` complex creation and the
  complex branches of `tolist()` / `item()` all raise `NotImplementedError` (verified in
  musapy-python ops.rs / array.rs). Both belong to the Phase 5 prerequisite task (P5.1).
- **GPU-less development**: keep `MUSAPY_MOCK_MUSA` mock mode. All math library FFI
  needs mock stubs in `musa_x_ffi.rs` so `cargo test` and CPU pytest run without hardware.
- **License constraint**: musapy is MIT. CPU FFT **must not link FFTW** (GPL-2+
  copyleft conflict) — use a pure-Rust radix-2 implementation (P5.6). Host linalg uses
  OpenBLAS (BSD-3, MIT-compatible).

management depend on it). Phases 2-8 are mutually independent and parallelizable.

## Phase 3: linalg B — lu / qr / svd

> **Status**: P3.1–P3.6 implemented (2026-08-07, validated numerically on real
> hardware; SDK findings recorded in ADR-003 003-D8 — gesvd V output is already Vᵀ,
> SINGULAR-mode U corruption worked around by ALL-mode slicing).

**Goal**: decomposition ops (muSOLVER) aligned to LAPACK / `torch.linalg` return
semantics (note: NumPy has no `np.lu` / `np.linalg.lu`; lu's return convention follows
`torch.linalg.lu`).

### Tasks

| Task ID | Task | Deliverable | Basis |
|---|---|---|---|
| P3.1 | lu: `musolver?getrf` → returns `(lu, piv)` (`(LU, pivots)` aligned with `torch.linalg.lu` / LAPACK getrf layout, piv 1-based int64) | linalg.rs | L4-1 |
| P3.2 | qr: `geqrf` + `orgqr` (real S/D; complex uses `cungqr` C/Z, both present in 3.1.0) → `(q, r)`; `mode='reduced'/'complete'` | linalg.rs | L4-1 |
| P3.3 | svd: `musolver?gesvd` (verified present S/D/C/Z in 3.1.0; `gesdd` absent, not a fallback) → `(u, s, vh)`, s descending; `full_matrices` semantics | linalg.rs | L4-1, risk register |
| P3.4 | CPU fallback: LAPACKE `?getrf/?geqrf/?orgqr/?gesvd`; naive pure-Rust if absent (svd via Jacobi iteration) | linalg.rs | host-lib strategy |
| P3.5 | Python export: `ms.lu` / `ms.qr` / `ms.svd` | ops.rs / lib.rs | v0.2 convention |
| P3.6 | tests: degenerate matrices (rank-deficient/zero singular values), non-square, `full_matrices` shapes | tests | Acceptance |

### Interface Signatures

```python
ms.lu(a) -> (lu, piv)                          # torch.linalg.lu semantics (LAPACK getrf layout); NumPy has no np.lu
ms.qr(a, mode="reduced") -> (q, r)             # 'reduced' | 'complete'
ms.svd(a, full_matrices=True, compute_uv=True) -> (u, s, vh)  # s 1D descending
```

## 14. Acceptance Criteria

### 14.1 Functional

| Criterion | Test |
|---|---|
| matmul shape semantics (1D/2D mixing) | `(n,)@(n,m)→(m,)`, `(m,n)@(n,)→(m,)`, `(m,n)@(n,k)→(m,k)` |
| matmul/solve numeric correctness | random matrices vs NumPy, allclose 1e-5 |
| solve singular error | singular raises `LinAlgError`; non-square raises `ShapeError` |
| qr decomposition | `q@r ≈ a` and `qᵀq ≈ I` (reduced/complete modes) |
| svd decomposition | `u@diag(s)@vh ≈ a`; s descending; full_matrices shapes correct |
| lu decomposition | `(lu, piv)` aligned with `torch.linalg.lu` / LAPACK getrf (permutation restore `p[a] = l@u`) |
| random seed reproducibility | same seed → elementwise equal |
| random distribution statistics | 1e6 samples mean/variance within 3σ |
| fft roundtrip | `ifft(fft(x)) ≈ x`; matches `np.fft` allclose |
| rfft shape | output `(N//2+1,)`; `n` truncate/pad semantics |
| spmv/spmm correctness | vs dense manual computation 1e-6 |
| sparse invalid input | indptr inconsistency / out-of-bounds raise errors |
| axis=tuple reduction | matches NumPy (keepdims/negative axis/axis order) |
| complex reduction | sum/mean real/imag correct; max/min raise `DtypeError` |
| boolean mask | `a[a>2]` shape/values correct; always copy |
| fancy indexing | `a[[0,1]]` correct; out-of-bounds raises Python built-in `IndexError` |

### 14.2 Non-Functional

| Criterion | Target |
|---|---|
| matmul f32 1K×1K throughput | < 10% gap vs direct mublas call (FFI overhead negligible) |
| fft 1M elements f32 throughput | ≥ 70% of direct muFFT (async pipeline measurement, existing bench methodology) |
| per-op CPU + MUSA test coverage | 100% of new ops have dual-path tests |
| handle/workspace leaks | mem_stats flat after 1e6 calls |
| build time (clean, incl. 5-lib FFI + openblas) | < 5 minutes |
| mock-mode full test suite | `cargo test` + pytest all green without GPU |

## Appendix A: Standard Checklist for Adding a Math Op

Using linalg `matmul` as the example:

1. `rust/musapy-core/src/musa_x_ffi.rs`: verify `mublasSgemm` etc. against `mublas.h`,
   add extern decl (real) + mock stub (same signature)
2. `rust/musapy-core/src/math_handle.rs`: confirm handle acquire/release path (register if new)
3. `rust/musapy-ops/src/linalg.rs`: `pub fn matmul(...)` (shape derivation → FFI call → post)
   + CPU fallback (`cblas_sgemm` or naive)
4. `rust/musapy-ops/src/lib.rs`: `pub use linalg::matmul;`
5. `rust/musapy-python/src/ops.rs`: `#[pyfunction] pub fn matmul(...)` (with debug-frame block)
6. `rust/musapy-python/src/lib.rs`: `m.add_function(wrap_pyfunction!(ops::matmul, m)?)?;`
7. `rust/musapy-python/src/array.rs`: `__matmul__` dunder (if applicable)
8. `python/musapy/__init__.py`: add import block + `__all__`
9. `python/musapy/_core.pyi`: `def matmul(...)` stub (+ dunder stub)
10. `tests/python/test_linalg.py`: CPU + MUSA-gated tests (vs NumPy)
11. If new external link (new MUSA-X lib or host lib): extend `musapy-ops/build.rs`
    linking/probe first (musapy-core/build.rs stays musart-only, L2-3)
