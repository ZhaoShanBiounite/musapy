## 003-D1: MUSA-X FFI Layer Placement & L2-3 Boundary Clarification

**Extends / clarifies**: L2-3 (Core Runtime responsibilities & prohibitions), L2-1 (Build System)

**Decision**:

| Component | Placement | Rationale |
|---|---|---|
| `musa_x_ffi.rs` (extern decls + mock stubs for the 5 libs) | **musapy-core** | same layer as musa_ffi.rs; decls & handles are infrastructure |
| `math_handle.rs` (handle/plan/generator/workspace lifecycle) | **musapy-core** | L2-3 responsibility table lists a "MUBLAS handle table" |
| compute calls (gemm/getrf/fft/spmv etc.) | **musapy-ops only** | L2-3 forbids op implementation/dispatch in core |
| MUSA-X link directives (`cargo:rustc-link-lib=mublas/musolver/murand/mufft/musparse`) | **musapy-ops/build.rs** | linking follows the caller; core stays musart-only |

**L2-3 boundary clarification**: L2-3's prohibition "calling MUBLAS/MUDNN/MCCL" is
interpreted as **compute dispatch** (issuing numeric work such as gemm); extern declarations
and handle lifecycle management (Create/Destroy/SetStream/version queries) are **not**
prohibited — L2-3's own responsibility table lists the "MUBLAS handle table" as core
thread-safe global infrastructure. The L2-3 comment in musapy-core/build.rs ("does not link
mublas/mudnn/mccl") **remains valid**: core emits no MUSA-X link directives; the extern
decls resolve at final link time of the musapy-python cdylib after musapy-ops emits the
linking.

**Rationale**:
- Centralizing declarations in core guarantees mock stubs and real FFI share signatures
  (same L2-3 pattern as musa_ffi.rs).
- Rust linking semantics: `cargo:rustc-link-lib` emitted by any crate in the dependency
  graph applies to the final binary, so "decls in core, linking in ops" is workable and
  cleanly separated.
- Keeps musapy-core free of compute-library .so dependencies; core stays compilable in
  runtime-only environments.

**Impact**:
- musapy-core gains musa_x_ffi.rs / math_handle.rs; lib.rs re-exports.
- musapy-ops/build.rs extends linking + openblas probe (see 003-D4).
- Implementation plan: v0.3-alpha-plan Phase 1.

## 003-D2: Handle Model & Lifecycle (musolver Shared Handle)

**Extends**: L2-3 (handle table), L3-9 (deferred-free), L3-10 (dealloc stream selection)

**Decision**:

**4 handle types per device** (lazy creation, per-device cache, cross-op reuse):

| Handle | Serves | Notes |
|---|---|---|
| `mublasHandle_t` | muBLAS **+ muSOLVER** | shared (see below) |
| `murandGenerator_t` | muRAND | Philox4x32_10 / DEFAULT engines |
| `mufftHandle` | muFFT | plan pool, keyed by (shape, type, direction) |
| `musparseHandle_t` | muSPARSE | generic API (SpMV/SpMM) |

**musolver has no own handle (verified on SDK 3.1.0)**: there is no `musolverDnHandle_t` /
`musolverDnCreate` (unlike cuSOLVER). Every routine takes `mublasHandle_t`, e.g.
`musolverSgetrf(mublasHandle_t handle, ...)`, and returns `mublasStatus_t`. Therefore
muBLAS and muSOLVER share one `mublasHandle_t`.

**Lifecycle rules**:
- Creation: lazy on first use; creation failure raises `DeviceError`.
- Stream binding: before each op call, `mublasSetStream` / `musparseSetStream` /
  `murandSetStream` binds the op's stream (v0.2 "every op passes its stream" convention).
  No stream type conversion needed: `MUstream` and `musaStream_t` are both
  `struct MUstream_st*` (verified in musa.h / driver_types.h).
- Release: on device teardown or process exit, via the **deferred_free queue** (L3-9
  default path); dealloc stream follows L3-10's last-used-stream policy.
- Workspace: muSOLVER / muSPARSE two-phase (`buffer=nullptr` query → alloc → reuse),
  size-bucketed cache; workspace buffers also use stream-ordered release.

**Rationale**:
- 2026-08-06 header-level audit (musolver_functions.h / mublas internal headers /
  musparse-functions.h).
- Handle create/destroy is expensive (driver-state resources); cross-op reuse is mandatory;
  deferred_free is the validated 3.x SDK release path from v0.1/v0.2 (L3-9 test matrix).

**Impact**:
- math_handle.rs provides a unified `with_mublas_handle(device, stream, |h| ...)` style API.
- Leak regression: mem_stats flat after 1e6 handle create/destroy cycles
  (v0.3 plan P1.7 / §14.2).

## 003-D3: Error Model Extension (LinAlgError + Built-in IndexError)

**Extends**: L3-5 (exception hierarchy), L3-6 (Python built-in inheritance)

**Decision**:

| Scenario | Exception | Notes |
|---|---|---|
| singular `solve` / factorization failure (getrf info > 0, etc.) | **`LinAlgError`** (new, subclass of `MusapyError`) | aligned with `numpy.linalg.LinAlgError` semantics |
| advanced indexing (mask / fancy) out-of-bounds | **Python built-in `IndexError`** | NumPy-compatible; no new musapy class |
| complex max/min/argmax/argmin | `DtypeError` (kept from 002-D3) | complex has no total order |

**Hierarchy constraint**: L3-5's shallow two-level hierarchy is unchanged — `LinAlgError`
is a direct subclass of `MusapyError`. **Single inheritance**: PyO3 `create_exception!`
supports single inheritance only; consistent with the v0.2 implementation (L3-6's
multiple-inheritance scheme was already implemented as single inheritance in v0.2; this
decision continues that).

**Rationale**:
- `numpy.linalg` raises `LinAlgError`; NumPy index OOB raises built-in `IndexError` —
  muscle memory (L0-1).
- Singularity detection happens in the ops layer (getrf info / zero-diagonal check on U),
  no kernel involvement.

**Impact**:
- musapy-core error.rs: new LinAlgError variant; musapy-python error.rs:
  `create_exception!` registration + `to_pyerr` mapping; OOB goes through
  `PyIndexError::new_err`.
- `python/musapy/__init__.py` exports `LinAlgError`; `_core.pyi` updated.

## 003-D4: CPU Fallback Host-Library Strategy

**Clarifies**: relationship with L4-2 (which defers the **standalone `musapy-cpu` crate**,
v2+); extends L2-1 (build probes)

**Decision (revised 2026-08-07)**: v0.3+ math-library ops are **GPU-only — no CPU fallback**;
calling them on a CPU device raises `DeviceError` (`linalg::require_musa`). CPU-device
support for pre-v0.3 ops (elementwise/comparison/reduction/creation/indexing) is **unchanged**.

Superseded decision: v0.3 math-lib CPU fallback as in-op embedded paths (linalg via
OpenBLAS + naive pure-Rust degradation; fft/random/sparse pure-Rust). Superseded because:
- mock mode (`MUSAPY_MOCK_MUSA`) already provides GPU-path test coverage without hardware;
  the CPU fallback's testing value was redundant;
- the OpenBLAS system dependency plus dual-path (openblas/naive) dispatch added
  significant maintenance and verification cost (two semantic bugs surfaced in the
  openblas path during this phase);
- math libs (muBLAS/muSOLVER etc.) are inherently GPU libraries with no CPU counterpart.

**Current impact**:
- linalg.rs (matmul/dot/solve): GPU-only; CPU input → `DeviceError::Mismatch`
  (consistent with math_handle's existing CPU rejection).
- musapy-ops/build.rs: OpenBLAS probe removed (formerly emitted `musapy_openblas` cfg).
- Test matrix: MUSA real device + mock (GPU stubs), two paths.
- Later phases (qr/svd/eig/random/fft/sparse) follow this policy; no CPU paths will be built.

## 003-D5: Complex Semantics

**Extends**: 002-D3 (complex reduction deferral, delivered by this decision), L4-1

**Decision**:

**v0.3 complex enablement scope** (complex64 / complex128):

| Layer | Content |
|---|---|
| kernels | elementwise: binary add/sub/mul/div + unary neg/abs; reduction: sum/mean (separate real/imag reduction) |
| math libs | linalg complex (Cgemm/Zgemm, complex getrf/getrs/geqrf+cungqr/gesvd), full fft suite |
| Python side | `ms.array` complex creation (incl. Python complex literal inference), complex branches of `tolist()` / `item()` |

**Semantic rules**:
- `max/min/argmax/argmin` **permanently reject** complex → `DtypeError` (002-D3's v0.2
  interim rule becomes permanent: complex has no total order).
- comparison: `eq/ne` support complex; `lt/gt/le/ge` reject complex → `DtypeError`
  (NumPy behavior).
- type promotion: reuse the CAT_COMPLEX rules already implemented in `dtype.rs`
  (JAX-style): float+complex → complex of the larger component width (f32+c64→c64,
  f64+c64→c128); int+complex → exact promotion.
- Python complex literal creation: `ms.array([1+2j])` infers **complex128** by default
  (NumPy behavior); `dtype=` overrides.
- `fft` output is always complex; `ifft` normalization 1/N (NumPy convention).

**Rationale**:
- 002-D3 explicitly deferred complex sum/mean; v0.3 delivers; fft (L4-1) hard-depends on
  complex.
- Verified in v0.2: `ms.array` complex creation and the complex branches of tolist/item
  raise NotImplementedError (ops.rs / array.rs); they must land together with the kernels,
  otherwise the §1.3 definition of success is unreachable.

**Impact**:
- elementwise.mu / reduction.mu gain complex instantiations (minimal mcc 3.1.0 smoke first,
  see risk register).
- musapy-python ops.rs / array.rs lift the complex NotImplementedError branches.
- complex instantiations of creation.rs fill/arange init kernels are **out of v0.3 scope**
  (zeros-complex can be temporarily covered by a fill=0 cast path; full support deferred).

## 003-D6: dot Op Supplement

**Extends**: L4-1 (the linalg row lists matmul/lu/qr/svd/solve and **does not include
dot**; this decision supplements it)

**Decision**: v0.3 adds `ms.dot(a, b)`:

| Input shapes | Semantics | Implementation |
|---|---|---|
| (n,) · (n,) | inner product → **0-dim** | `mublasSdot/Ddot/Cdotu/Zdotu` (complex **non-conjugating**, NumPy semantics → dotu) |
| (m,n) · (n,k) | = matmul | delegates to the matmul path (003-D7) |
| N-D broadcast dot | **unsupported** (evaluate v0.4+) | NumPy N-D dot is sum-product over axes |

**Rationale**: dot is high-frequency; implementation cost on top of matmul/mublas is
minimal. Its absence from L4-1 is an omission, recorded here per the main ADR's usage
notes item 2.

**Impact**: linalg.rs + export `ms.dot` + `Array.dot()` (no new dunder; `@` is matmul).

## 003-D7: Math Library Python API Shape & Return Conventions

**Extends**: L4-1, L3-18 (naming conventions within the `__array_function__` v1 scope)

**Decision**:

**API shape**:

| Domain | Shape | Example |
|---|---|---|
| linalg | **module-level functions** + `__matmul__` dunder | `ms.matmul(a, b)`, `a @ b`, `ms.solve(a, b)` |
| random / fft / sparse | **namespace submodules** | `ms.random.rand(...)`, `ms.fft.fft(...)`, `ms.sparse.csr_matrix(...)` |

Namespaces follow the `np.random` / `np.fft` / `scipy.sparse` muscle memory (L0-1).

**Return conventions** (NumPy-aligned unless noted):

| Op | Convention |
|---|---|
| `ms.svd(a, full_matrices, compute_uv)` | `(u, s, vh)`, s 1D **descending** (NumPy semantics) |
| `ms.qr(a, mode)` | `(q, r)`, `mode='reduced'/'complete'` (NumPy semantics) |
| `ms.lu(a)` | `(lu, piv)`, aligned with **`torch.linalg.lu`** / LAPACK getrf layout (piv 1-based int64). Note **NumPy has no `np.lu`**; it is not the reference |
| `ms.solve(a, b)` | solves `a·x = b`; singular → `LinAlgError` (003-D3); non-square → `ShapeError` |
| `ms.fft.ifft` | normalization 1/N; supports `norm='ortho'` (NumPy convention) |
| `ms.fft.rfft` | real input → complex output, shape `N//2+1` |
| `ms.random.*` | optional per-call `seed=`; same seed → elementwise reproducible |
| `ms.sparse.csr_matrix/coo_matrix` | standalone lightweight types (**not** Array subclasses); support `@` (spmv/spmm) and `.toarray()` |

**Rationale**:
- lu has no NumPy counterpart; `torch.linalg.lu`'s `(LU, pivots)` layout is the native
  LAPACK getrf output, allowing a zero-copy passthrough of musolver getrf results — lowest
  implementation cost.
- svd/qr/fft NumPy conventions are the user-expectation baseline (L0-1).

**Impact**:
- musapy-python gains random.rs / fft.rs / sparse.rs submodules; python/musapy gains
  random.py / fft.py / sparse.py wrappers.
- `_core.pyi` and `__init__.py` exports updated; tests follow the §14.1 acceptance matrix.

## 003-D8: Decomposition Ops Implementation Notes (2026-08-07 real-device probe corrections)

**Extends**: 003-D7 (lu/qr/svd return conventions) — SDK 3.1.0 findings corrected during
Phase 3 implementation via C probes on real hardware.

Two probe conclusions contradicted the initial header-level reading and were fixed
in the implementation:

| # | Probe finding | Impact |
|---|---|---|
| 1 | `musolver?gesvd` **V output buffer already holds Vᵀ** (header: "stored as rows (transposed)"; probe 2: reconstruction error 1e-15 reading V' column-major vs 4.1 reading V) | `vh` = strides `(1, ldv)` view, **not** `(n, 1)` |
| 2 | **SINGULAR mode corrupts U for m>n** (probe 3: 6×4 gives UᵀU−I=4.5, reproduced with both OUTOFPLACE and INPLACE; same matrix under ALL mode: 1e-15) | Always use ALL/ALL + thin strided-view slices (first k cols/rows of the full buffers), bypassing SINGULAR entirely |
| 3 | SINGULAR-mode V buffer is written compactly with leading dim `min(m,n)` (larger ldv corrupts output; probe 2, wide 3×5) | Merged into fix #2 (SINGULAR no longer used) |

**Decision**:
- `ms.svd` internally always uses `MUBLAS_SVECT_ALL` (`NONE/NONE` when
  `compute_uv=False`); thin outputs (u m×k / vh k×n) are strided-view slices of the
  full-size buffers — **zero extra copies**.
- Singular-value sanity check (all S ≥ 0 and finite) backs up unreliable `info`
  (getrf info unavailability proven in Phase 2, 003-D3; probes show gesvd writes info=0).
- lu/qr have no additional mode issues: getrf/geqrf/orgqr follow header signatures with
  column-major materialized input + strided-view outputs.

**Impact**: implementation constraint of `linalg.rs svd`; docs note that SDK 3.1.0
SINGULAR mode is unusable (re-evaluate after SDK upgrade to save memory).
