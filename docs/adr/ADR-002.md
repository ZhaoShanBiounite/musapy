## 002-D1: Type Promotion for Binary Ops

**Extends**: L1-5 (JAX type promotion), L1-14 (GPU precision alignment)
**Supersedes**: the v0.1-alpha constraint "binary ops require equal input dtypes" (an implementation simplification in v0.1, never an ADR decision)

**Decision**: From v0.2, binary elementwise and comparison ops **no longer require** equal input dtypes.
The result dtype is computed by `promote(a, b, all_gpu)` (main ADR L1-14 rules); inputs are cast to the result dtype before the operation.

**Implementation strategy** (to bound kernel complexity):
- elementwise/comparison kernels are **only instantiated for same-dtype** forms (`<T,T>→T`, comparison `<T,T>→bool`); no template specialization per `(in_a, in_b, out)` triple.
- When an input dtype ≠ result dtype, the ops layer first inserts an internal `astype` cast (itself a stride-aware elementwise op, see 002-D2) to cast the input to the result dtype, then calls the same-dtype kernel.
- Cost: one extra cast pass. Benefit: the kernel matrix drops from O(N³) to O(N), and the existing v0.1 same-dtype kernel path is reused.

**Rationale**:
- L1-5 already mandates the JAX promotion table; `promote()` is implemented and exported in musapy-core but unused in v0.1. v0.2 is the right time to activate it.
- The equal-dtype constraint forces manual `astype`, violating NumPy/CuPy muscle memory (the L3-5 error model serves the same goal).
- "Cast first, then same-dtype kernel" is a common compromise (used by CuPy and others) that avoids combinatorial explosion.

**Impact**:
- Comparison ops always return `bool`; the two inputs are first promoted to a common input dtype, then compared.
- `ms.add(int32_array, float32_array)` on GPU → L1-14 → `f32`; the int32 input is cast to f32.
- The cast path requires `astype` as v0.2 internal infrastructure (also exposed publicly as `Array.astype()`).
- CPU fallback and mock stubs follow the same "cast first, then same-dtype compute".

## 002-D2: Broadcast = elementwise strides=0

**Extends**: L4-1 (broadcast row: "implemented via elementwise strides=0"), L1-11 (0-dim Array)

**Decision**: Broadcast is not a separate mechanism; it is the **per-operand stride** capability of elementwise kernels.
The broadcast shape follows **NumPy rules**: align from the rightmost dimension; each dimension must be equal or one of them must be 1 (or one operand is 0-dim).
For a broadcast dimension, the operand's stride is set to **0**, so the kernel's index does not advance along that dimension → the element is replicated.

**Kernel ABI change** (common to elementwise/comparison):

```c
// v0.1 ABI (add only, flat contiguous):
void musapy_add_f32_v1(const float* a, const float* b, float* c, size_t n, musaStream_t s);

// v0.2 ABI (stride-aware, N-dimensional):
void musapy_add_f32_v2(
    const float* a, const float* b, float* c,
    int ndim,
    const size_t* shape,     // broadcast output shape, length ndim
    const ssize_t* a_strides,// in ELEMENTS, length ndim; broadcast dims are 0
    const ssize_t* b_strides,
    musaStream_t s);
```

- Output `c` is always **contiguous** (standard row-major strides); c_strides is not passed.
- Strides are in **elements** (not bytes); the kernel addresses via `a[idx·stride]`.
- An input may itself be non-contiguous (e.g. a transpose view); its strides are **composed** with the broadcast strides before being passed.
- Symbol version `_v2`: the `_v1` symbol was retained within v0.2 per L4-3 (as an internal 1D-contiguous fast path), but **removed in P6 cleanup (2026-08-04)** — the Rust layer never called it and `_flat_v2` covers the same functionality.

**0-dim scalar broadcast**: an operand with `shape=[]` broadcasts to any shape; all its dimension strides are 0 (L1-11: a scalar is a 0-dim Array, no special code path).

**Rationale**:
- L4-1 already locked broadcast to strides=0; this decision provides a concrete ABI.
- NumPy broadcast rules are the existing intuition of scientific users (L0-1 primary audience).
- Always-contiguous output simplifies downstream (reduction/indexing may assume contiguous output).

**Impact**:
- Phase 1 must complete the ABI rework first, then rewrite `add` on the new ABI; all other elementwise/comparison ops then reuse it directly.
- `common.h` needs N-dimensional index→linear-offset helpers (e.g. `offset_nd(idx, strides, ndim)`).
- Broadcast shape computation + stride derivation live in the ops layer (Rust); kernels contain no broadcast logic (per L2-2: no dispatch in kernels).

## 002-D3: Reduction Semantics (axis / keepdims / accumulation dtype)

**Extends**: L4-1 (reduction row), L1-14 (dtype policy; this decision clarifies its boundary in the reduction case)

**Decision**:

| Item | Rule |
|---|---|
| `axis` | v0.2 supports `None` (full reduction → 0-dim) and `int` (single axis). `tuple` multi-axis is **deferred** to late v0.2 or v0.3 |
| `keepdims` | `bool`, default `False`; when `True`, reduced dimensions are retained with length 1 |
| negative axis | supported; `axis < 0` → `axis + ndim` (NumPy behavior); out-of-range raises `ShapeError` |

**Accumulation / output dtype rules** (aligned with NumPy/CuPy, correctness-first):

| Op | Integer input | Float input | Output dtype |
|---|---|---|---|
| `sum` / `prod` / `cumsum` | accumulate in int64 | keep input dtype | int→int64; float→input dtype |
| `mean` | accumulate in float64 | float32→float32, float64→float64 | always float |
| `max` / `min` | keep | keep | input dtype (no accumulation) |
| `argmax` / `argmin` | — | — | always int64 (indices) |

- bool input: `sum` counts as int64; `max/min` return bool.
- Complex: v0.2 reductions **do not support** complex (`max/min/argmax/argmin` have no total order for complex) → raise `DtypeError`; complex `sum/mean` deferred.

**Rationale**:
- Integer accumulation overflow is a **correctness** issue, taking priority over L1-14's "narrow-first" (which targets elementwise **performance**).
- argmax/argmin output indices; int64 is the NumPy/CuPy convention.
- Complex numbers are unordered; max/min semantics do not hold — an explicit rejection is better than a misleading result.

**Impact**:
- Reduction kernels need block-reduce (`common.h` gains block-reduce helpers); `mean` = `sum / count` (count = number of reduced elements).
- Axis reduction traverses by that axis's stride; output shape derived per keepdims.
- `cumsum` is a scan needing a separate kernel (prefix sum); v0.2 first supports cumsum along `axis`.

## 002-D4: Indexing Semantics (view-vs-copy / negative index / step)

**Extends**: L4-1 (indexing row), L3-27 (Array naming — one Buffer, many views)

**Decision**:

| Op | Implementation | view / copy | Needs kernel |
|---|---|---|---|
| `transpose(a, axes=None)` | rearrange Layout strides | **view** | no |
| `permute(a, dims)` | transpose with explicit dims | **view** | no |
| `flip(a, axis)` | negate stride + adjust offset | **view** | no |
| `slice` (`a[i:j:k]`) | adjust offset + strides + shape | **view** | no |
| `gather(a, indices, axis)` | fetch elements by index | **copy** | yes (indexing.mu) |
| `scatter(a, indices, values, axis)` | write elements by index | **copy** (returns new Array) | yes (indexing.mu) |

**Slicing details** (aligned with NumPy):
- Negative index: `i < 0` → `i + dim_len`.
- step: positive/negative step supported; negative step equals flip + positive step.
- Out-of-bounds: start/stop are **clamped** to the valid range (NumPy behavior, no error); empty slices are legal (that dimension has length 0).
- v0.2 implements **basic slicing** only (integer / slice). **Advanced indexing** (boolean mask indexing, fancy indexing with integer arrays) is deferred to v0.3+.

**View semantics guarantees**:
- A view **shares the Buffer** with the original Array (via `BufferRef`, per L1-10 read/write reference separation); mutating the view mutates the original data.
- A view's `name` is independent of the original Array (L3-27: the motivation for name living on Array, not Buffer, is precisely multiple views).
- Views are usually **non-contiguous**; because elementwise is stride-aware (002-D2), views can participate in subsequent ops directly, without a copy first.

**Rationale**:
- L3-27 explicitly states name lives on Array because "one buffer can have multiple views (slice/transpose)" — this decision realizes that hint.
- Zero-copy views are performance-critical (transpose/slice must not trigger D2D copies).
- Advanced indexing semantics are complex (boolean indexing returns a copy, shape hard to predict); deferring reduces v0.2 risk.

**Impact**:
- transpose/permute/flip/slice need only Rust-side Layout manipulation + a new `BufferRef`, **no kernel, no allocation**.
- gather/scatter need `indexing.mu` (a new `.mu` file; build.rs must compile it).
- `Layout` gains pure-function transforms: `transposed(axes)` / `sliced(range)` / `flipped(axis)`.

## 002-D5: dtype and device Resolution for Init Ops

**Extends**: L0-6 (device 5-level chain), L0-7 (dtype 5-level chain, level-5 = float32), L0-9 (first creation requires explicit device), L3-18 (`*_like`)

**Decision**:

| Op | dtype source | device source |
|---|---|---|
| `zeros` / `ones` / `full` | L0-7 chain: `dtype=` param > `with ms.dtype()` > global default > **float32** | L0-6 chain: `device=` param > `with ms.device()` > global default > auto-probe |
| `eye` | same as zeros/ones (nothing to infer → L0-7 chain → float32) | same |
| `arange` | **inferred from arguments** (NumPy behavior): all-integer args→int64, any float arg→float64; explicit `dtype=` overrides | same |
| `linspace` | default **float64** (NumPy behavior); explicit `dtype=` overrides | same |
| `zeros_like` / `ones_like` | **inherit the input Array's** dtype (ignore global default) | **inherit the input Array's** device |

**First-creation rule**: `zeros/ones/full/eye/arange/linspace` are all "first creation" candidates. If `ms.set_default_device()`
was never called and there is no `device=` param and no `with ms.device()` context, then per L0-9 raise `DeviceNotConfiguredError` (do **not** silently auto-probe).

**Rationale**:
- zeros/ones/full/eye have no argument to infer dtype from, so they fall to L0-7 level-5 (float32) — consistent with the library's GPU float32 default.
- arange/linspace inferring dtype from arguments is NumPy muscle memory (`ms.arange(3)` → int64, `ms.arange(3.0)` → float64).
- `*_like` inheriting the input is explicit L3-18 scope and matches the "like = same shape and type" intuition.
- The L0-9 first-creation rule applies equally to init ops, keeping a consistent "explicit device" experience (L0-1).

**Impact**:
- Init kernels are "write-value" kernels: zeros/ones/full are fills (write a constant by linear idx); arange/linspace are idx→value; eye is a conditional write (`i==j`).
- Init ops must populate `DeviceResolution`/`DtypeResolution` (L0-8 feedback), with source matching the resolution-chain level.
- arange's integer/float inference happens in the ops layer (Rust); kernels are still instantiated per the resolved dtype.
