- **设备**: MTT S4000（MUSA，mp_22 架构，驱动报告 56 CUs / 47.9 GB VRAM）
- **规模**: 1,048,576 elements × f32（4 MB/数组），50 次迭代，全异步流水 + 首尾 sync
- **方法**: `benchmark/bench_musa_utilization.py` 输出 + 实现代码探查（elementwise/reduction/indexing kernel 与 host 路径）

## 2. 瓶颈排名

### 🔴 P0（正确性）: cumsum 大数组结果错误 + smem 越界

- `musapy_cumsum_scan_sums_kernel_v2`（`kernels/reduction.mu:286`）**单 block 256 线程**扫描每行的 block sums，smem 仅 `256 × sizeof(T)`。
- `blocks_per_row = ceil(axis_len / 256)`（`op_builder.rs:2408`）。当 **axis_len > 65536**（1D 数组 > 65536 元素即踩中）：
  - 第 256 个之后的 block sum 永远不会被扫描，前缀保持 0 → **累计结果错误**；
  - `sdata[idx]` 在 idx ≥ 256 时**越界写共享内存**（未定义行为）。
- Rust 侧无任何防护（`op_builder.rs:2408` 直接算 blocks_per_row）。
- **benchmark 中 1M 元素 cumsum 的 0.252ms 测的是错误结果**；测试套件全用小数组，未暴露。
- 修复方向：分层扫描（两级 prefix）或 host 侧限制 axis_len ≤ 65536 并报错。

### 🔴 P1: gather/scatter 全量 indices ~10ms（40x 于等价拷贝 0.24ms）

- 每次调用无条件执行 `read_indices_host`（`indexing.rs:200` / `:350`）= `stream.synchronize()` + 8MB 同步 D2H + O(n) host 越界校验循环。
- 每次迭代都串行化整条 GPU 流水线，并破坏 benchmark 的异步计时。
- 规模相关性验证：8 个索引 0.096ms → 262K 索引 2.66ms → 1M 索引 9.9ms（纯 D2H 拷贝时间）。**非 kernel 瓶颈**。
- 修复方向：GPU 常驻 indices 信任 + kernel 内 clamp 越界（PyTorch 语义，kernel 改动已设计过：`GatherMeta` 增加 `in_axis_len`）；或校验移出热路径。
- 预期收益：~10ms → ~0.3ms（40x）。

### 🟠 P2: reduction 全局 34 GB/s（0.124ms）；2D 小矩阵 1.6-2.1 GB/s（0.126-0.161ms）

**全局（axis=None，1M）**：
- 两阶段：partial kernel（grid=3907 blocks，**每线程仅 1 元素** + 8 轮 `__syncthreads` 树归约）+ final kernel（grid=1）。
- 0.124ms = 0.07ms 固定地板 + ~0.05ms GPU 时间（每 block 归约延迟链，4MB 只到 ~80 GB/s，非带宽受限）。

**2D 小矩阵（256×256 = 256KB）**：
- `axis_len ≤ 1024` 走 naive 路径：`grid = ceil(out_size/256)`。256×256 时 **grid=1 —— 整个 GPU 只有 256 线程在跑**。
- 对照：同样数据 cumsum(axis=1) 用 256 blocks（每行一个），0.068ms。**并行度相差 256x**。
- 根因：naive/parallel 路径选择只看 axis_len，不看总工作量（out_size × axis_len）；归约用 smem 树 + 8 次 barrier 而非 warp shuffle。
- 修复方向：每线程 4-16 元素 + float4 加载；warp shuffle 归约；路径选择按总工作量；小 axis 按段分块。
- 预期收益：全局 0.124 → ~0.08ms；2D 0.126-0.161 → ~0.07ms。

### 🟠 P3: elementwise ~57-60µs/op 固定地板（"210 GB/s"是派生量，非带宽上限）

- 11 个算子延迟**完全相同**（0.058-0.061ms），与流量（8 vs 12 MB）和计算量（add vs sin）无关。
- 关键证据链：
  - view 算子（无 kernel launch）= **1µs** → PyO3 / Rust / buffer pool 开销可忽略；
  - sum(global) 两 kernel = 74µs vs cumsum(axis=1) 一 kernel = 68µs → **第二个 launch 只 +6µs**；
  - 结论：~55-60µs 的地板在**每次 op 调用的首个 kernel launch 路径**（MUSA driver 提交/调度），不在应用层。
- 全部 kernel 无 float4 向量化、每线程 1 元素（`kernels/elementwise.mu` 仅 `_flat_v2` 标量快路径），但 1M 规模下 GPU 执行时间（30-60µs @ 200-400 GB/s 标量流式）≈ 地板，被掩盖。
- 修复方向：应用层只能减少每逻辑 op 的 launch 次数（kernel 融合）+ 增大 payload；float4 向量化在 ≥4M 元素时才显效。
- 验证手段：`--size` 从 1M 扫到 64M —— 若延迟随 size 线性增长即坐实。

### 🟡 P4: contig(transp)/contig(flip) 34 GB/s — 转置拷贝非合并访问

- copy kernel（`kernels/indexing.mu` `musapy_copy_kernel`）逐元素 `offset_nd`。
- 转置视图读 stride=(1, 1024)：warp 内 32 线程地址相隔 4KB → 每 4B 读一个独立 sector，浪费 8-32x 事务。
- flip（负 stride）反序读行内仍近连续，34.5 GB/s 同档。
- 修复方向：tiled smem 转置 kernel。
- 预期收益：34 → 150-250 GB/s（~6x）。

### 🟡 P5: benchmark 方法学瑕疵（非实现问题）

- `log` 记的是 `ms.log(ms.abs(a))` —— **双 kernel**（0.120ms ≈ 两次 launch，并非 log 本身慢），带宽/算力按单 kernel 记账，系统性低估。
- reduction 2D 专项用 256KB 矩阵 → launch 开销主导，脚本的 `--size < 1M` 警告在该专项不生效。
- elementwise 的 GB/s 数字在 1M 是固定地板（P3）的派生量，需 ≥10M 才有真实带宽意义。
- gather/scatter 数字是"同步 D2H + host 校验"的串行路径延迟（已加注释），非 kernel 性能。

---

## 3. 结论

1M 规模下几乎所有数字都受 **"每次 op 调用 ~60µs 固定地板 + 每额外 launch ~6µs"** 主导；GPU 768 GB/s 带宽远未饱和。
唯一例外是 gather/scatter —— host 侧每次 D2H 校验的串行路径（P1，40x 差距）。

优化优先级建议：**P0（正确性）→ P1（40x）→ P2（2x）→ P4（6x，针对转置物化）→ P3（需 ≥10M 规模才有意义，先做向量化）**。
