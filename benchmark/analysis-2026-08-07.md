# Benchmark 分析（2026-08-07）：v0.3 全量重跑 + linalg/random 瓶颈归因

分支 `feat/v0.3-musax-ffi`（HEAD `874a077`）。全部数字在 MTT S4000（mp_22, 56
CUs, 47.9 GB VRAM）实机测得，**release 构建**（`maturin develop --release`；
此前 venv 内是 debug 构建，host 侧逐字节循环慢 10-100×，本次已重装）。

运行内容（排除 `bench_math_handles.py`——它是句柄生命周期回归，非性能基准）：
`bench_linalg.py`、`bench_musa_utilization.py`（1M + 10M 两档）、`bench_random.py`，
外加 C 段级探针（`/tmp/probe_solver3.c`，g++ 直连 muSOLVER/muBLAS）与 Python
黑盒差分探针。原始输出：`/tmp/results-2026-08-07/`。

## 1. 总览

| 项 | 结论 |
|---|---|

## 2. linalg 段级归因（C 探针，1024² f64，每迭代恢复输入）

### 2.1 solve：真凶是奇异检测 D2H，不是 getrs

| 段 | 耗时(ms) |
|---|---|
| col_major_copy（转置+物化） | ~1 |
| B1 getrf-only | 17.2 |
| B2 getrf + sync + D2H 对角 | 43.7 → **D2H = 26.5** |
| B3 全 solve（+getrs） | 50.9 → **getrs = 7.2** |

- solve(1024) 51ms = copy 1 + getrf 17.2 + **memcpy2D 26.5** + getrs 7.2。
- 8KB 跨步 D2H `musaMemcpy2D`（`linalg.rs:896`）逐行 8B 传输，**每行 ~26µs
  驱动开销**；连续 8KB `musaMemcpy` 仅 0.18ms（**145× 差距**，实测对照）。
- 此前推断的「getrs 病态 ~34ms」**被推翻**——getrs 本身只有 7.2ms。
- 差分探针交叉验证：solve−lu 差值随 n 线性增长（2.1/7.9/32.0ms @64/256/1024），
  与「每行 26µs × n 行」完全吻合。
- **修复方向（musapy 侧，收益最大）**：设备端 kernel 提取 LU 对角到连续缓冲
  （一次 launch，~20µs）+ 连续 8KB D2H（0.18ms）→ 奇异检测从 26.5ms 降到
  ~0.3ms，**solve(1024) 51ms → ~25ms（-50%）**。更进一步可直接设备端判奇异，
  只回传 4B 标志。

### 2.2 qr：geqrf 本身是 SDK 瓶颈

| 段 | 耗时(ms) |
|---|---|
| C1 geqrf-only | 258.7 |
| C2 geqrf + orgqr | 437.8 → orgqr ≈ 179 |
| R 提取（host 中转） | ~8（release） |

- 与 getrf 同为 O(n³) 分解（工作量仅 ~2×），geqrf 却慢 **15×**——SDK 3.1.0
  的 geqrf 实现（f64 非分块/低效路径）是瓶颈，orgqr 次之。
- **f32 qr(1024) = 365ms**（仅比 f64 快 1.2×）→ 与 f64 仿真无关，SDK geqrf/
  orgqr 本身低效。应用层无解，记入 SDK 限制。

### 2.3 svd：ALL 2.7s，NONE 只省 25%

| 模式 | 耗时(ms) |
|---|---|
| gesvd ALL/ALL | 2695（musapy 2708 ✓） |
| gesvd NONE/NONE | 2016（**仅 -25%**，256² 同样 0.76×） |

- `compute_uv=False` 逃生通道收益有限——SDK 的 NONE 模式仍做大部分迭代工作。
- 探针教训：gesvd 原地破坏 A，未恢复输入时迭代不收敛（3s → 54s）；musapy
  每调用 `col_major_copy` 新鲜输入所以恒 2.7s。

### 2.4 matmul：f64 封顶 ~160 GFLOPS 坐实

| n | sgemm GFLOPS | dgemm GFLOPS | d/s 比 |
|---|---|---|---|
| 512 | 1365 | 97.2 | 14.0× |
| 1024 | 7568 | 156.3 | 48.4× |
| 2048 | 14038 | 159.1 | 88.2× |

- f32 曲线继续爬升（~14 TFLOPS，未封顶）；**f64 在 1024 即封顶 ~160 GFLOPS**，
  比 f32 慢 88×，且比值随规模持续恶化（14→88×）——mp_22 无原生 FP64 的
  软件仿真 + DGEMM kernel 调优不足的双重特征。影响所有 f64 分解算子，应用层
  无解，文档化性能预期。

### 2.5 dot：带宽未封顶在 200，64M 达 450 GB/s

| n | sdot 延迟(ms) | 带宽(GB/s) |
|---|---|---|
| 1M | 0.185 | 43（地板主导） |
| 4M | 0.227 | 141 |
| 16M | 0.411 | 311 |
| 64M | 1.139 | **450**（DRAM 峰 683 的 66%） |

- 修正此前「~200 GB/s 封顶」推断（那是 10M 以下的读数，曲线仍在上升段）。
- 自研 sum kernel 64M 仅 200 GB/s（final 阶段 1 block 串行，08-04 已预告残留）
  →「自研 reduction 替换 mublas dot」**不成立**；两者都非带宽最优，但 mublas
  dot 更好。若做替换需先解决 reduction final 多 block 化。

## 3. elementwise 新发现：标量广播路径 2-4× 慢

| 运算（100M） | 延迟(ms) | 带宽(GB/s) |
|---|---|---|
| add f32（同形） | 1.79 | 447 |
| mul f32×标量 | 8.38 | **96**（4.7×） |
| add f64（同形） | 6.12 | 262 |
| mul f64×标量 | 11.05 | 145 |

- 归因：binary kernel 每元素 `offset_nd(idx, ...)`（`kernels/elementwise.mu:42`）
  对 0-dim 标量操作数仍做 N 维索引分解 → mp_22 上 64 位 div/mod 软件仿真
  （P1 同类问题，修复时已覆盖 gather/scatter/copy 但 elementwise 标量路径未覆盖）。
- 影响面：`random.uniform`（= rand + 标量 mul + 标量 add，100M f64 多 ~6ms）、
  `random.bernoulli`（= rand + 标量 lt，100M f32 多 ~5ms）、以及任何用户标量运算。
- **修复方向（musapy 侧）**：0-dim/strided-0 操作数快路径——标量读入寄存器/
  smem 一次广播，跳过逐元素 offset_nd；或复用 P1 的 32 位/ndim==1 快路径。

## 4. random 套件

| op × dtype | 1M | 10M | 100M |
|---|---|---|---|
| rand f32 GB/s | 64 | 284 | 169（100M 退化） |
| rand f64 GB/s | 101 | 256 | 149 |
| randn f32 GB/s | 45 | 233 | 161 |
| randn f64 GB/s | **1.4** | **2.8** | **3.1** |

- **randn f64 ~3 GB/s 坐实**（SDK 3.1.0 `murandGenerateNormalDouble` 病态，
  ~100× 慢于 f32），normal f64 同价（transform 成本可忽略）。文档化。
- rand 100M 带宽退化（284→169 GB/s）：murand kernel 规模特征，SDK 侧。
- uniform f64 = rand + 标量 mul + 标量 add，100M 实测 28.7ms（分解 5.3+11.1+10.9
  吻合）；曾测得 176.7ms 为驱动瞬态异常（与 OOM 同类，复测 28.7ms）。
- bernoulli 100M = 9.0ms：rand 2.4 + 标量 lt（~5ms，见 §3）。

## 5. utilization 与基线对比（无回归）

1M 延迟视角与 08-04 基线一致：sum 0.085 / argmax 0.091 / gather 0.177 /
scatter 0.240 / contig(transp) 0.063 / contig(flip) 0.104ms；2D 专项
sum(axis=0) 0.056ms。10M 带宽视角：elementwise 490-567 GB/s（受 45µs 地板
稀释，与 08-04 的 620-655 GB/s @16M+ 一致）、comparison 410 GB/s、
reduction 162 GB/s、argmax 129 GB/s、cumsum 46 GB/s、gather 61 GB/s
（随机访问非合并本质，08-04「kernel 本体 ~320 GB/s」说法在 10M 不成立）、
contig(transp) 232 GB/s、contig(flip) 123 GB/s。

残留项确认：reduction final 串行段（sum 64M 200 GB/s）、arg* 小 axis naive
路径、cumsum 分层扫描 46 GB/s、f64 无 double2 向量化（add f64 262 vs f32
447 GB/s 的构成部分）、flip 专用 kernel。

## 6. 驱动级发现（探针副产物）

1. **`musaMemcpy2D` 小 pitch D2H 非确定性**：同一参数（dpitch=8, width=8,
   D2H）在不同上下文表现随机——error 1 / 进程段错误 / 2.2s stall / 26ms /
   正常。musapy solve 路径（创建流 + sync 前置）实测稳定，但属侥幸；已在
   §2.1 的修复中顺带绕开（改设备端 kernel + 连续拷贝）。
2. **bench_random 尾部瞬时 OOM**（`musaMalloc: out of memory`）：非确定性，
   完整流程复刻通过；musapy 记账全程干净（每配置 Allocated=0）。判定为驱动
   大块分配/回收瞬态，建议基准侧对 OOM 容错（该段已非计时核心）并记入 SDK
   限制。

## 8. 方法学备忘

- 探针必须**每迭代恢复输入**（gesvd/geqrf/getrf 原地破坏 A，否则后续调用在
  垃圾数据上测出 54s/4.98s 的伪数字）。
- 计时须与 musapy 同构：创建流 + handle 绑定 + sync 前置，避免默认流/未同步
  状态下触发驱动慢路径。
- 1M 规模读数全为 45µs 地板伪影；f32/f64 对比至少用 ≥1024。

### P3 证伪细节（保留备查）
- mcc double2 支持探针 PASS（`/tmp/probe_vec2.mu`，`LD.B128`/`ST.B128` 反汇编确认）。
- 启用条件照抄 vec4：contiguous + n≥1M + n%2==0 + 16B 对齐；对齐（vec2）与
  未对齐视图 `[1:]`（flat）同规模对照，3 组均 flat 相等或略快。
- 结论：f64 elementwise 在 16M-100M 的带宽（433-634 GB/s 视 op/规模）不由
  加载宽度决定；f32 float4 的 +5% 亦属边缘收益。f64 相对 f32 的带宽差
  （如 add f64 433 vs f32 620+）需从内存子系统/访存模式角度另行调查。
